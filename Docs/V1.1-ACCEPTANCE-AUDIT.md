# v1.1 — Phase 9 Acceptance-Test Audit

**Date:** 2026-08-30. **Scope:** the final v1.1 acceptance-test audit (analysis, no
large rewrite). Companion to `Docs/V1.1-ADDON-ARCHITECTURE-PLAN.md` (Phase 9) and
`Docs/ADDON-API-DESIGN.md` (§3 governing rule, §7 tensions, §8 verdict).

## The acceptance test
Delete the add-on's manifest → the DLL loses ZERO PROGRESSION-SPECIFIC lines. General
host MACHINERY (allocation engine, widgets, co-save framing, manifest reader, general
primitives) is fine to keep. A line is a VIOLATION only if it exists solely to serve
progression's specific DESIGN/JUDGMENT (a class ratio, a perk verdict, a hardcoded
progression string/layout) with no add-on driving it.

## VERDICT: **PASS-with-noted-residuals**

The DLL is a general add-on host. With no manifest it degrades cleanly and holds no
LIVE progression behavior. The residuals are: (a) ONE compiled-in design-judgment table
(`kEntryPoints[92]` perk verdicts) that is INERT when the add-on is absent (gated behind
`g_detected`), flagged since Phase 0 §3 #2 for a post-v1.1 lift; (b) save-compat
machinery that names the add-on's plugin variants, which the frozen-reader invariant
(#12) requires and which is not progression design/judgment. No live progression ratio,
verdict, layout, or content renders or executes when the manifest is gone.

## Item-by-item verdicts (the 4 audited residuals)

### 1. `AddonVerb` → backend dispatch (Board `ApplyEdits`, Board.cpp 3080-3137) — **KEEP (general host plumbing)**
The carrier is fully generic: `EditKind::AddonAction` + an `AddonVerb` enum
(`SetClass/AllocPerk/Respec/SetManual/ApplySkillPoint`) + an arg-union
(`{verbId, follower fid, form arg, param}`). The switch body routes each verb to
`ProgAllocator::` — but `ProgAllocator` is the general **allocation HOST**, not the
add-on, and the five verbs are a general allocation-verb vocabulary any allocation
add-on would use (set class, allocate perk, respec, toggle manual, apply a manual
skill point). No verb encodes a class ratio, a perk verdict, or a progression layout.
The generation-guard, `BoardEditScope`, and `MainThread::Post` hop are host machinery.
**Not a violation.** The stale comment at Board.cpp 3078 ("stays progression-shaped
until Phase 7/9 routes it through the manifest") overstates the residual — Phase 7
found the allocation math already data-driven, and this dispatch is a fixed general
vocabulary, not progression judgment. (Comment left as-is to keep this docs-only; a
one-line comment refresh is the only optional cleanup here.)

### 2. Board tab BODY + view payload (`BoardProgSnap`/`BoardFollowerView`/`BoardNodeView`, Board.cpp ~1251-2440) — **KEEP (general widgets fed by data), residual = composition not yet manifest-declared**
The body renders **zero progression CONTENT**: every string/coordinate is DATA —
class names (`prog.classes`, `who->clsName` from MESG.FULL), perk-node names/descriptions
(`nd.name`), skill rows, and the perk-dome geometry/labels (all from the frozen catalog:
`gridX/gridY/hpos/vpos/parentIndices/verdict`). The only hardcoded strings are generic
widget CHROME ("Respec", "Take rank N", "Apply 1 skill point", "Manual skill points",
"Choose class...", "Class: " prefix, "Skill"/"Level"/"Perks" headers, zoom +/-) — the
host widget's own captions, carrying no class name/ratio/verdict (confirmed in Phase 6c's
widget-chrome accounting). The perk dome is a general host widget (§7 #4). The type NAMES
(`BoardProgSnap` etc.) are progression-flavored C++ symbols carrying general data — the
same call Phase 8 made for the PRGN co-save symbols (a mass rename of a render-critical
file is churn with zero acceptance-test benefit).
**Residual (soft):** the widget **composition** (which widgets appear, in what order:
class-picker → perk-dome → skill-table) is still HARDCODED in Board.cpp rather than read
from a manifest-declared composition (the §3/§7 #4 "add-on declares composition only"
ideal). But a fixed arrangement of three GENERAL widgets is a general "allocation tab"
shape, not progression content, and it renders nothing when `snap.boardTabs` is empty
(delete the add-on → `DrawFieldKit` iterates zero hosted tabs, Phase 6a seam). Verdict:
not a content violation; formalizing composition-as-data is a nice-to-have, low priority.

### 3. `kEntryPoints[92]` perk-effectiveness verdict table + `ClassifyRank` (Progression.cpp 65-158, 322) — **FIX (design judgment), post-v1.1 follow-up; INERT when absent**
This is the ONE compiled-in progression JUDGMENT still resident. Each row assigns
`kEffective/kMarginal/kDead` to a BGSEntryPoint index; the comment states it verbatim:
"the verdicts are the design's lists verbatim ... judgment calls on values the design
left unnamed, biased toward marginal." That effective/marginal/dead trichotomy — and the
bias — encode progression's thesis of "what makes a follower build good," which drives
auto-perk-picking. Per §3 #2 / §7 #3 this is progression OPINION → should be manifest
`entryPointVerdicts[]` data, no DLL default.

**Recommendation — SPLIT (do NOT move now; large generator change held for marth):**
- KEEP in the DLL as a general engine fact: the perk **walk** (`ClassifyRank`'s
  enumeration of a perk's entry types, quest/ability/entry-point dispatch, the
  CommonLib-churn-resistant int compares) and a general "does this entry point produce a
  real effect for a non-player NPC" classification — that half is a genuine engine fact
  ANY follower-buffing add-on wants ("ModBuyPrices does nothing for a follower").
- LIFT to the manifest as data: the effective/**marginal**/dead editorial verdicts and
  the marginal-bias policy — progression's filtering judgment.

**Why PASS-with-residual and not a hard fail:** the catalog build (the only caller of
`ClassifyRank`/`kEntryPoints`) is gated on `g_detected` (Progression.cpp:693,
`if (!g_detected && !dump) return`). With no add-on the table never executes and
influences nothing user-visible — it is dead data compiled into the binary. So the
acceptance test's SPIRIT (delete add-on → no progression BEHAVIOR) holds; only its
LETTER (a progression-judgment table still ships in the DLL) is imperfect. Priority:
low, post-v1.1 (92 verdicts → ESL records is real generator work for no live-behavior
gain, since the shipped add-on's verdicts reproduce the table exactly).

### 4. Sweep for other DLL-resident progression judgments/strings/constants
Swept `native/*.cpp|.h` for hardcoded class names, ratios, layouts, and "Progression"-
flavored strings.
- **`HmsProfile` class ratios** — CLEAN. Phase 7 generalized it: `HmsProfile(stance)`
  walks `g_classes` for the matching ClassDef and returns its normalized
  `hmsWeights[]`/`primaryPool`; no DLL default (no class → false → HMS reshapes nothing).
  The 60/5/35 etc. literals are gone.
- **`kClassNames[4]` = {Auto, Melee, Ranged, Mage}` (Board.cpp:318)** — CLEAN, general.
  These are the BASE Gambit combat-class names (`combatClassOverride` 0..3, a base
  feature since Phase 2), rendered on the FOLLOWER tab (Board.cpp:762), NOT progression's
  manifest classes. Same for `CombatStyle.cpp` StanceToStr. General base-feature vocab.
- **`MFO_Progression.esl`/`.esp` plugin-name literals** — the only genuinely add-on-
  SPECIFIC strings in the DLL. Two sites, both save-compat MACHINERY, neither progression
  design/judgment:
  * `LookupAddonForm` ESL↔ESP sibling resolver (ProgAllocator.cpp:2703-2704) — resolves
    a class-identity across the add-on's two shipped plugin-name variants (the Vortex
    ESL + the ESP variant). **KEEP** (save-safety read path; the task forbids co-save
    changes). Optional far-future nicety: derive the sibling-name pair from discovered
    manifests instead of a literal pair — but that is not a design-judgment violation.
  * pre-v3→v4 legacy migration `kProgPlugin`/`kClassDefLocal[3]` (ProgAllocator.cpp:2936-
    2939) — synthesizes plugin-qualified identity for pre-v3 saves that only ever came
    from MFO_Progression at fixed ordinals. **KEEP FOREVER** (frozen reader, invariant
    #12; old saves carry a bare ordinal that only meant something for that one add-on —
    unfixable by design, and inert for any save >= v3).
- **Chrome strings mentioning "progression":** Board.cpp:1311 empty-state
  ("...to manage progression.") and ProgAllocator.cpp:2326 refusal tooltip
  ("Progression INACTIVE until a class is set") — minor host-widget captions. Could use
  the manifest tab label instead; not changed here (altering user-visible text is not a
  byte-identical trivial cleanup). Cosmetic residual, negligible.

No hardcoded class ratio, perk verdict beyond item 3, or progression layout was found
outside the items above.

## Absent-add-on trace (degrade cleanly, host intact and inert)
With no manifest (`Manifests()` empty, `g_detected`/`g_ready` false):
- **Discovery:** `Progression::Init` scans, finds no manifest keyword, sets
  `g_detected=false`, logs one line "no addon manifests found — progression off"
  (Progression.cpp:680-685). No error.
- **Catalog:** `if (!g_detected && !dump) return` (Progression.cpp:693) — the catalog
  (and `ClassifyRank`/`kEntryPoints`) never builds. The verdict table is dead.
- **Allocation:** `g_ready=false`; every verb refuses with a named line —
  `Enroll`/`SetClass`/`AllocatePerk`/`Respec`/`SetManualSkills`/`ApplyManualSkillPoint`
  all early-return on `if (!g_ready) ... "refused: addon absent"` (ProgAllocator.cpp
  2264/2334/2386/2479/2529/2568). Nothing mutates a follower.
- **Board tab:** `CopyBoardTabViews` iterates `Manifests()` (empty) → zero
  `BoardTabView`s; `DrawFieldKit` iterates `snap.boardTabs` → zero hosted tabs
  (Phase 6a/6b seam). No progression tab renders.
- **Co-save:** `CoSaveSave` is UNGATED (writes even when absent, by design, so a
  temporarily-disabled ESL's state survives) — but with nothing enrolled `g_prog` is
  empty, so it writes only the header + `count=0`, zero add-on bytes
  (ProgAllocator.cpp:2713-2735). Old PRGN v1–v6 readers stay forever (#12).
- **No crash.** The general host stays compiled and intact (walk, widgets, co-save
  framing, level poll, manifest reader), fully inert.

## Progression still FUNCTIONAL with the add-on present (strangler invariant)
Data path spot-checked intact: manifest keyword discovered → `ParseClassDef` builds
`g_classes` (names/skills/perkPriority/hmsWeights, all manifest data) → `BuildGenericManifests`
mirrors to `Manifests()` and sets `g_ready` → `Enroll`/`SetClass`/allocation run the
economy-GLOB/INI-driven math → `CopyBoardTabViews` publishes a `BoardTabView` per declared
tab → the board body binds the published `BoardProgSnap` and renders class picker + perk
dome + skill table from catalog data. HMS reads the manifest `hmsWeights` via the
generalized `HmsProfile`. No phase broke the live path.
