# v1.1 — Add-On Architecture Rework (phased plan)

**Goal (marth's ruling):** the DLL exposes a WIDE GENERAL follower API and acts as a
general add-on HOST that reads an add-on's SELF-DECLARATION ("I am a progression tab,
here is my design"). NO new Papyrus, NO add-on-specific C++ in the DLL — **delete the
progression add-on and MFO.dll loses ZERO lines.** Also folds in the HMS release
blocker (HMS becomes a base feature, class from the base Gambit tab).

**Three outcomes this rework must deliver:**
1. **Full removal** — progression logic leaves the DLL entirely (Phase 9 acceptance test).
2. **Vortex fix** — the manifest MUST be self-contained: the DLL discovers the add-on by
   scanning loaded plugins for a self-declared record, and the add-on carries **NO master
   on MFO.esp**. That kills the ESL-masters-ESP reciprocal/load-order cycle that breaks
   Vortex today (the reason a separate .esp variant exists). "No cross-master reference"
   is a HARD requirement of the manifest design (Phase 0/4).
3. **Reference example** — with zero add-on-specific DLL code, the progression add-on
   becomes the worked public example of the general add-on API.

**Working rules for this rework:**
- One chunk at a time, each independently CI-green + reviewable, low-token.
- Progression stays FUNCTIONAL after every chunk (no big-bang; incremental strangler).
- Document each chunk's outcome in this file (append a "DONE" note) as we go.
- Co-save-touching chunks get the heavy adversarial review; the rest get a light diff review.
- **NO field testing / NO deploys BETWEEN phases (marth 2026-08-26).** All testing is stalled
  until the ENTIRE v1.1 pass (all phases) is complete; then ONE test pass. Merge CI-green chunks
  to main (progression stays functional), but do NOT push builds to custom-modlist/Tuxborn and
  do NOT ask for field results until the full pass is done. Any per-phase "field test" notes
  below are the END-OF-PASS test plan, not a mid-pass action.

**Current footprint (baseline, 2026-08-26):** ProgAllocator.cpp 2911 + .h 361,
Progression.cpp 689; Board.cpp ~106 progression refs; Config ~41 refs; PRGN co-save
record (Serialization, kProgVersion 5); partial infra already: `AddonRef`, `Addons()`,
`kAddonSentinel 0x803`.

## Phase 1 — General follower API surface (extract primitives)
Define + expose the DLL's general follower-mutation API (SetSkill/GetSkill, GrantPerk/

## Phase 2 — HMS becomes a BASE feature + fix the class read (RELEASE BLOCKER)
Move HMS off `ProgState::clsId`/ClassDef onto the base Gambit class
`FollowerState::combatClassOverride` via a `Followers::` accessor. Root-cause and fix
"Mage reads as Melee" (a class SET/resolve bug affecting skills too). See
[[hms-v2-base-feature-and-fixed-stat-grant]]. Review: HMS steers by the base class,
works with the add-on absent. Done: Jesper (Mage) shows the Mage HMS profile.

**ROOT CAUSE FOUND (2026-08-26, code + po3 docs, high confidence):** `ClassDef.stance` is
matched from a GLOB by editor-id suffix (`_Stance`), but the engine DISCARDS editor-ids for
TESGlobal at runtime (`GetFormEditorID()` returns "" for globals; keywords/armor keep theirs,
which is why other MFO editor-id reads work). So `EdidEndsWith(glob,"_Stance")` never matches →
EVERY class stance parses 0 → `HmsProfile(0)` false → `RecomputeHMS` early-exits before it even
logs (no `[hms]` for anyone) AND `SetClass` mirrors `combatClassOverride = 0` (Auto) → melee
behavior. Manifest DATA is correct (generator declares Mage stance 3). SAME bug silently kills
every economy GLOB knob (why the INI seeds were needed). Confirm on the DECK log: `[prog] class
"..." ... stance 0`, `GLOB ... does not end "_Stance" — ignored`, `GLOB ... matches no economy
knob — ignored`. Melee-SKILLS is a separate thread (skills key on AVIF FormID, works) → `clsId`
points at the Melee def; SET path is clean so the pick likely never landed on Mage — the added
`[hms-diag]` line settles it.

**marth's call (2026-08-26): SHIP THE UNBLOCK (B) ONLY.** Minimal, EditorID-free: (1) HMS stance
comes from `Followers::GetBaseClass` (base Gambit class) not `def->stance`; (2) `SetClass` STOPS
clobbering `combatClassOverride` with the broken stance (Gambit tab is the stance authority; the
progression-tab pick sets the SKILL class only); (3) fold in one `[hms-diag]` line (clsId,
defName, def->stance, baseClass, early-return, budget) to confirm the fix + the clsId identity.
DEFER (A) fixing GLOB reads (po3 exported editor-id / structural) — economy stays on INI seeds.
Keep HMS on the progression poll/ProgState for now (full add-on-absent divorce is later).

## Phase 3 — Fixed-stat HMS grant (RELEASE BLOCKER)
Detect fixed-stat NPCs (0 engine HMS award); tally NPC total HMS vs the player's; once
the player catches up, grant the NPC HMS at the player's per-level point rate by class;
retroactive. Player-HMS tracking + co-save state (extend the still-unshipped v5 block).
Review: HEAVY (co-save). Done: a fixed-stat mage gains Magicka once the player passes it.

## Phase 4 — Add-on self-declaration manifest (format + reader)
Define the manifest an add-on ships (class defs, per-level allocation rules, MCM control
list, board-tab layout) as ESL records/data. DLL reads it into a generic in-memory model.
Review: schema covers everything progression needs. Done: the manifest parses, unused yet.

## Phase 5 — Host the add-on MCM tab from the manifest
DLL renders the add-on's MCM tab + Config from its manifest, replacing the hardcoded
progression MCM/Config globals. Review: audit_mcm still green; toggles behave. Done:
progression MCM comes entirely from the manifest.

## Phase 6 — Host the add-on board tab from the manifest
DLL renders the add-on's board tab from its manifest, replacing the hardcoded progression
tab in Board.cpp. Review: board renders + interacts as before. Done: the ~106 Board.cpp
progression refs are gone / generic.

## Phase 7 — Allocation logic as data + general primitives
Express skill/perk allocation (class weights, scarcity pool, revert-engine-awards,
perk-tree walking) as data + event-rules over the API. Where a rule can't be data, add a
GENERAL API primitive — never progression-specific C++. Likely sub-divides. Review:
allocation matches today's behavior. Done: ProgAllocator's progression math is data-driven.

## Phase 8 — Co-save: general add-on-state slots (HEAVY REVIEW)
Replace the PRGN-specific record with general "add-on state" slots: an add-on stores its
state via a general API, the DLL serializes it generically (keeping PRGN readers forever
for old saves). Review: HEAVY adversarial save-safety pass. Done: progression state rides
a general slot; old PRGN saves still load.

## Phase 9 — Verify + cleanup + ship v1.1
Remove the progression add-on's C++ hooks; confirm deleting the add-on's manifest makes
the DLL lose ZERO progression-specific lines (the acceptance test). Final review, cut v1.1.
